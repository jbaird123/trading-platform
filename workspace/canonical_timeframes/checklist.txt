Canonical Timeframe Standardization Checklist

Goal: ensure every configuration, cache, dataset, and code path uses the same canonical timeframe names (e.g., `5min`, `15min`, `1h`, `4h`, `1d`, `1w`) so there are no legacy prefixes creeping into caches, briefs, or reports.

1. **Canonical registry definition**
   - [x] Expand `trading_platform/data/timeframe_aliases.py` into a full alias registry (map every legacy prefix to a pandas-style canonical label).
   - [x] Provide helper APIs (`canonicalize_timeframe`, `canonicalize_column_name`, `column_from_feature`) plus documentation for the registry.
   - [x] Include reverse lookup if we ever need to display legacy names to users.

2. **Manifest + config normalization**
   - [x] Normalize every `feature.timeframe` when loading `config/features/global.yaml` so the manifest only exposes canonical labels.
   - [x] Update `resolve_global_feature_manifest` and `select_minimal_global_features` to operate on canonical names and raise on unsupported aliases.
   - [ ] Normalize CLI args, RunConfig fields, and campaign plans that supply timeframes (execution timeframe, gating profile keys, `--timeframes` flags).

3. **Cache builder and metadata**
   - [x] Before writing parquets/metadata, rename every column (including `_bar_open/close/lookup_key`) to canonical names.
   - [x] Persist canonical names in `metadata.json` so loaders can trust the recorded schema.
   - [x] Ensure golden/test caches (`data/cache/global_features`, `workspace/.../cache`) only contain canonical columns.

4. **Cache loader/backtester context**
   - [x] Have `load_cached_global_features` select columns by canonical names, using helper mapping to handle legacy names when needed.
   - [x] Ensure `_execute_backtest_loop` builds contexts from canonical columns and writes canonical `context_at_entry/exit` keys to distilled artifacts.
   - [x] Update gating/classifier logic to expect canonical context features (the `context_at_entry_*` prefix should always be canonical).
   - [x] Normalize `global_feature_names` and guard-feature validations around canonical labels.

5. **CLI, campaigns, and scripts**
   - [x] Normalize timeframe arguments in `trading_platform.cli`: `--timeframes`, `global_features_mode`, campaign plan generator/resolver, etc.
   - [x] Update pipeline scripts (`run-backtest.sh`, `run-full-ml-pipeline.sh`, campaign-run outputs) to expect canonical column names.
   - [x] Document the canonical naming expectation for YAML configs, campaign configs, and CLI overrides.

6. **Persistence and reporting**
   - [x] Confirm `brief.json`, `trades.csv`, `signals.parquet`, `processed_data.parquet` emit canonical field names (e.g., `ctx_global_features_15min_...` instead of `ctx_global_features_m15_...`).
   - [x] Update reporting analytics, AI diagnostics, and verification tools to parse canonical names.
   - [x] Regenerate any golden/reference files so they match the canonical scheme.

7. **Tests & enforcement**
   - [ ] Add tests/assertions that metadata/caches never contain legacy prefixes.
   - [ ] Add CI checks or scripts that scan generated artifacts for non-canonical columns.
   - [ ] Update existing tests (golden validation, contextual features) to use canonical names and guard against regressions.

8. **Documentation & onboarding**
   - [ ] Document the canonical scheme and how to extend it in `workspace/canonical_timeframes/` or docs.
   - [ ] Provide usage examples for new feature authors (e.g., “always call `canonicalize_timeframe('m15')` before persisting column names”).
   - [ ] Once everything passes, remove any remaining legacy normalizations so there’s only one canonical path.

Success criterion: every artifact (config, cache metadata, context exports, campaigns, reports) only references canonical timeframe names, with automated checks preventing regressions.
